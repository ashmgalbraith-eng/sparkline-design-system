# Accessibility

## Role and ARIA

Input renders a native `<input>` element, which carries its own implicit `textbox` role. The component manages label association automatically — the visible `label` is linked to the input via `for`/`id`, so screen readers announce the label when the field receives focus.

- `aria-describedby` should reference `helperText` or `errorText` elements so contextual messages are read after the field label. Wire this up at the application level when embedding the component.
- When `state` is `'error'`, set `aria-invalid="true"` on the host or native input so screen readers announce the error condition.
- Icons inside the field are decorative; they carry `aria-hidden="true"` and do not affect the accessible name.

## Keyboard navigation

| Key | Behaviour |
|-----|-----------|
| `Tab` | Moves focus to the input (skipped when `state` is `'disabled'`). |
| Standard text keys | Type, delete, and navigate within the field as per browser defaults. |

## WCAG compliance

| Criterion | Level | Notes |
|-----------|-------|-------|
| 1.3.1 Info and Relationships | A | Label is programmatically associated with the input; helper/error text should use `aria-describedby`. |
| 1.4.3 Contrast | AA | Label text, input text, and border colours meet minimum contrast. |
| 2.1.1 Keyboard | A | Fully operable via keyboard using native input behaviour. |
| 2.4.7 Focus Visible | AA | A visible focus ring is applied to the input when focused. |
| 3.3.1 Error Identification | A | Use `errorText` to describe errors in text; set `aria-invalid="true"` when in error state. |
| 3.3.2 Labels or Instructions | A | Always supply a `label`; use `helperText` for format hints. |
| 4.1.2 Name, Role, Value | AA | Native `<input>` semantics handle role and value; ensure label association is correct. |
